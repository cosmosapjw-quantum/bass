# BASS v1.0 Work-harness audit and transplant report

## Verdict

The uploaded material is useful but unsafe and scientifically mis-scoped as a direct
installation. The two generic harness ZIPs collide at root paths; their validators accept
placeholder states. The automation kit contains a hard-coded successful verifier, a runner
that does not perform its advertised patch lifecycle, unsafe archive extraction, incomplete
gate execution, stale PATCH80R state, and permanent locks that would make a finished BASS
background runtime impossible to claim.

Accordingly, nothing was overlaid or executed. A new namespaced BASS harness was built from
the defensible concepts and locked to a background-only, convergence-controlled high-ell
scope. Solver implementation remains closed.

## Load-bearing findings

1. The research and coding archives have 11 colliding root paths; nine differ in content.
2. Their initialization scripts preserve shipped placeholders unless forced; force mode can
   destroy ledgers and is not atomic.
3. Their validators test file presence/headings, not populated contracts, authorization,
   evidence, high-ell obligations, or perturbation firewalls.
4. The legacy automation scaffold emits verifier booleans set to `True`; the patch runner
   merely unpacks, verifies/builds, and repackages, and the documented `--task-file` option
   is absent.
5. The automation runner uses unguarded archive extraction, omits promised gates, and the
   deterministic ZIP code erases executable modes and can follow symlinks.
6. Both adaptive CMB prompts are perturbation/transfer/likelihood oriented, force plots for
   every node, allow post-audit fixes without mandatory re-audit, and have no repair bound.
7. `bootstrap.sh`, the Rust environment script, and the partial Rust-core archive come from
   incompatible snapshots and cannot be combined into a trusted installation.
8. Rust 1.94.1 itself is authentic, but installation is unnecessary and unauthorized now.
9. `bianchi_phase_r` contains perturbation-era authority structures and shared formula/code
   lineage, so it can be an oracle but cannot automatically count as independent or become
   BASS production authority.

## Installed controls

- explicit no-code/no-execution authorization flags
- spatial-perturbation and likelihood firewall
- canonical metric, orientation, units, tetrad/connection, frame, and ray conventions
- all-11-family target without premature coverage claims
- high-ell closure/refinement, leakage, conservation, stiffness, limit, and backend gates
- feature/family claim ledger instead of readiness percentages
- machine-readable DAG with downstream invalidation
- bounded repairs, conditional plots, real receipts, runtime recovery, and external-oracle
  handoff contracts
- standard-library static validators with negative archive-path tests

## Current honest state

Only harness input provenance and the harness self-test may pass at this stage. No solver,
family, high-ell, polarization, collision, history, backend, output, or release claim is
supported. The next transition is owner scope confirmation, followed by read-only code
intake after the user uploads canonical work.

## Post-transplant hostile QA correction

An independent adversarial copy initially showed that a minimal PASS receipt, a supported
claim backed by a blocked gate, and an injected `src/solver.rs` could survive routine
manifest regeneration. The first validator also hard-coded the initial phase and made the
normal OD0-to-C0 transition circular. That draft was blocked and replaced before handoff.

The installed validator is phase-aware, separates code-read from implementation/build/
execution authorization, binds claim promotion to a fresh PASS gate receipt, detects stale
governing fingerprints with transitive invalidation, and runs explicit hostile regression
tests for all three mutations plus a positive OD0-to-C0 transition.

A second science-contract audit then blocked empty-but-`RESOLVED` owner values, ambiguous
sector names, shared family evidence, an unspecified neutrino mass, and an unreachable
production-upstream oracle choice. The final transplant therefore validates typed OD001–4
values and a hash-bound owner receipt, maps OD002 keys to conditional gate criteria and leaf
claims, locks disabled sectors out of scope, gives every family leaf isolated runtime/
constraint/limit criteria (including generic and exact exceptional VI_h branches), and
states the neutrino target as collisionless with exactly `m_nu=0`.

The follow-up adversarial pass also tested coordinated weakening, where matching rows are
deleted from a registry, claim ledger, and gate together. Immutable validator baselines and
negative tests now pin the 12 family-leaf criterion sets, nine sector claim/gate/channel
bindings, five high-ell row semantics, derived all-in-scope aggregates, and the explicit
massive-neutrino exclusion; mutual consistency alone is not accepted.

A final instruction-layer pass found two further fail-closed defects before sealing. First,
allowed prose such as `AGENTS.md`, `START_HERE.md`, and executor prompts could be changed
and re-manifested without staling H1. Second, an old PASS static log could be reused after
governed tools/tests changed. H1 and OD0 now hash the exact 53-file immutable standalone
payload (including all instructions, policies, prompts, tools, tests, and sealed bootstrap
history). Six phase/state JSON files remain live-mutable only for typed transition values;
their immutable projections still bind decision questions, transition rules, claim/gate/
node structure, and field schemas. Free-form run-state instructions were replaced by
validated machine codes. Static log v2 binds identical pre/post execution snapshots to
those governing bytes, and hostile tests reject instruction mutation and old-log reissuance.

OD0 was also completed as a real evidence transition rather than a phase-only assertion.
Its producer record binds only the stable owner-decision file, exact owner receipt, and
separate read-only authorization receipt, so later legitimate DAG/run-state evolution does
not stale OD0. The validator cross-checks the authorization action, narrow scope, explicit
confirmation, owner-receipt SHA-256, producer artifact, and OD0 gate-receipt references.

The final evidence-layer hostile pass further rejected two false-history paths. H0/H1
static records now carry a canonical command-plan fingerprint and are checked against
exact shell-free argv/cwd plus result-specific semantic outputs; both the producer and the
independent reviewer must rerun that plan. Separately, cumulative solver/oracle activity
flags are derived only from dedicated activity receipts that bind an explicit historical
action authorization, clean producer evidence, and an independent review. Reusing a
generic gate/evidence record or clearing the receipt registry cannot manufacture or erase
activity history.
